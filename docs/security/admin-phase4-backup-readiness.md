### Proposed private manifest/receipt contract to review before implementation

This is a private ceremony proposal, not an implemented schema or evidence. Use a new explicit schema/profile version and strict validation; unknown or missing required fields must fail. Suggested required fields:

- Identity: `schemaVersion`, `profile`, `ceremonyId`, `releaseSourceRevision`, immutable candidate/rollback artifact manifest hashes, `fixture:false`, target environment/realm, approved server/daemon/source-container identities and database inventory hash. Keep host locations/identities private.
- Archive creation: `archiveSha256`, `archiveBytes`, `createdAtUTC`, approved recipient certificate fingerprint, source image/version, exact non-template DB names, per-DB metadata/table summaries plus full-inventory digest, globals/schema/migration/grant digests, and quiescence checkpoint identity/time. Receipt verification time alone cannot establish checkpoint freshness.
- Capsule: ciphertext-bound aggregate configuration hash, expected file-inventory digest/count, role/config/checkpoint/vault binding attestation and required-key-presence outcomes. Do not publish file contents, credential hashes, hidden-state digests or raw OWNER identifiers. Detailed table/role/key evidence stays restricted.
- Tools: hashes of every executable/helper/import, snapshot SQL, runtime and verifier image; expected artifact/config profile. Producer and consumer must compare these values to independently approved expected hashes, not merely repeat self-reported values.
- Off-server evidence: approved distinct destination-host identity, private completed-copy reference, independently computed source/destination SHA-256 and byte count, completion/verification times and transfer completion checkpoint. Require equality to the exact archive restored; the verifier's legacy unconditional boolean is insufficient.
- Restore result: `verifiedAtUTC`, exact archive/copy binding, AEAD-before-restore result, actual isolation inspection result, restored DB/globals/inventory comparison digests, schema/constraints/triggers/roles/grants/settings/append-only/`pg_amcheck` outcomes, capsule-binding outcome and disposable cleanup success. Do not issue PASS if cleanup is incomplete.
- Admission: independent review identity/time, still-quiescent source recheck, private durable pending/completed state and ordinary security/health evidence identities/deadlines. Final admission rejects stale, mismatched, duplicate/conflicting or incomplete state. Receipt custody/mode/owner/link checks and exclusive durable publication are required; do not accept arbitrary JSON booleans from an untrusted path as proof.

The current 44-table admission constant is historical; the parent reports a 45-table current local fixture. Neither is authority to replace the real inventory with another fixed count. Establish the actual current target inventory under authorization and compare exact names/metadata, rather than relabelling a 44-table receipt or simply changing it to 45.

## Partial failure and rollback rules

- Before any deploy/migration/grant, backup/copy/restore failure requires no data rollback. Preserve encrypted evidence and pending/completed checkpoints. Either remain contained or use a separately accepted abort plan to restore only known-good runtime/ingress under fresh ordinary security/health controls. Resumed writes invalidate the old quiescent checkpoint for a later cutover.
- After a partial schema/grant/cutover operation, keep writes closed; reconcile exact committed state/receipts before retry. Never down-migrate, rewind Audit/history or remove OWNER/checkpoint locks to clear uncertainty. Restore a known-good configuration only with controller re-verification and `nginx -t`, preserving unrelated healthy services.
- Binary rollback must use the separately qualified Phase-3-plus-compatible artifact retaining Task 1 vocabulary/action/history parsers, restriction enforcement/expiry/reconciliation, one-row processed-command insert behavior, guarded first Room UPDATE arbitration and idempotent aborted-body admission cleanup/hard cap. Grant revocation alone does not erase durable new-key history.
- An actual data incident needs its own write-since-backup assessment, maintenance, Redis/outbox/job/idempotency reconciliation and explicit restore/cutover authorization. Never overwrite the live DB or delete volumes (`down -v`), and never substitute Redis for durable PostgreSQL evidence.
- No automatic credential rotation, PIN/pepper/command-key changes, bootstrap, recovery or lock removal. ADR-084's post-disaster session-invalidation requirement belongs to a separately approved recovery plan; it is not authority to rotate credentials during this release or rehearsal. Keep the command key needed for historical ciphertext.
- Retain the real encrypted archive, independent key and receipt for the approved rollback window; no automated deletion or invented retention/PITR/RPO/RTO promises. No load/stress/soak or Phase 5 is authorized here.

# ADR-084 — راه‌اندازی و بازیابی سادهٔ OWNER در Staging

- **Status:** Accepted؛ نسخهٔ خصوصی و پیش‌نیازهای ابزار با مجوز مالک در ۲۰۲۶-۱۰-۲۶ روی Staging نصب شدند. اجرای بکاپ واقعی، Bootstrap و Recovery همچنان مجوز جدا می‌خواهند؛ [رسید نصب](../implementation/admin-private-owner-installation-2026-10-26.md).
- **Owner:** مالک HamBazi برای اختیار اپراتور و custody؛ مهندسی برای پیاده‌سازی، تست و qualification نسخه.
- **Date:** 2026-10-26
- **Supersedes:** فقط الزام دو امضای Ed25519 و فایل حاوی credential در مراسم هویتِ realm/environment دقیق `staging` در ADR-079/081/083 و گزارش آمادگی قبلی. OWNER، RBAC، قفل PIN، Audit، OWNER_FINAL، حدود داده و تصمیم ingress تغییر نمی‌کنند.
- **Related:** [ADR-083](083-admin-public-https-and-self-credential-rotation.md)، [روش اجرایی](../operations/admin-owner-staging-ceremony.md).

## Context

مالک دو امضاکنندهٔ مستقل ندارد و مسیر سادهٔ خصوصی برای نخستین OWNER می‌خواهد. این کاهش پیچیدگی تصمیم جدید است، نه ادامهٔ یک پروفایل ساده‌شدهٔ ازقبلپیاده‌شده. ابزار قبلی هنوز دو proof و فایل credential خام می‌خواست. فقدان کلید نباید به fallback مخفی، seed، SQL مستقیم یا HTTP unlock منجر شود. Staging فعلی یک مالک/اپراتور اصلی و زیرساخت SSH موجود دارد؛ production در این تصمیم نیست.

## Decision

طبق تأکید مالک، OWNER هیچ قابلیت Forgot/Reset Password ندارد. فقط تغییر Password/PIN از نشست کامل با احراز مجدد مجاز است؛ Recovery خصوصی نیز Password فعلی را حفظ می‌کند و به همان Password نیاز دارد. نگه‌داری امن رمز اصلی بر عهدهٔ مالک است.

1. پروفایل صریح `staging-ssh-root-v1` فقط با realm و environment هر دو `staging`، policy نصب‌شدهٔ root، UID صفر، SSH مجاز و TTY منطبق، پرچم تأیید و تأیید تعاملی همان عملیات اجرا می‌شود. هیچ گزینهٔ عمومی `skip-signatures` وجود ندارد. فایل policy، audit، checkpoint و credentialهای DB خصوصی‌اند؛ والدهای symlink یا قابل‌نوشتن توسط دیگران و فایل‌های دارای permission نامناسب/hardlink رد می‌شوند.
2. ابزار `admin:owner:staging` تنها ورودی Staging است؛ composer قدیمی فایل‌محور realm `staging` را رد می‌کند. مسیر دو امضا برای محیط‌های دیگر باقی است. هیچ endpoint، startup job یا credential در کانتینر runtime اختیار این مراسم را نمی‌دهد؛ roleهای bootstrap و recovery جدا می‌مانند.
3. نخستین Bootstrap با اختیار root در SSH و تأیید مستقیم مالک انجام می‌شود. در این پروفایل، **اختیار معتبر اپراتور، نمایندهٔ اختیار مالک Staging است؛ اثبات رمزنگاری مستقل دو شخص ادعا نمی‌شود**. پروفایل private-host فقط طبق policy آدرس و CA کانتینری را به IP خصوصی دارای SAN و CA موجود میزبان تبدیل می‌کند؛ secret/نام DB و verify-full حفظ و هیچ config سرویس یا DNS تغییر نمی‌کند. Username/Password/PIN را خود مالک انتخاب و همگی با echo خاموش وارد می‌کند؛ Password/PIN تکرار می‌شوند. هیچ secret در argv، فایل درخواست، چت، output، history کاربردی یا Audit نوشته نمی‌شود. core dump و ابزار debug/trace فعال رد می‌شوند؛ ضبط ترمینال/TTY و keylogger باید در محیط اجرا غیرفعال و با اپراتور تأیید شوند. برنامه در برابر root یا سیستم‌عامل مخرب تضمین ندارد.
4. capability پنج‌دقیقه‌ای فقط در حافظهٔ همین فرایند، پس از کنترل‌های خصوصی ساخته و به realm/subject/action/commandId و HMAC digest ورودی نرمال‌شده متصل است. JSON ارسالی، مقدار مشابه capability، DB credential یا session مدیر نمی‌تواند آن را بسازد. Password/PIN همچنان با Argon2id، salt مستقل و pepper موجود حفاظت می‌شوند؛ KDF و authority پیش از transaction کوتاه‌اند.
5. singleton و binding مالک در PostgreSQL حفظ می‌شوند. پیش از اثر، checkpoint بیرون DB شامل commandId/action/digest و وضعیت pending اتمیک/fsync می‌شود؛ raw secret و username ندارد. موفقیت، همان ownerId را در checkpoint نهایی ثبت می‌کند. crash/commit نامعلوم pending را حفظ می‌کند؛ فقط همان درخواست می‌تواند resume شود. تغییر digest، ثبت OWNER دوم یا restore قبل enrollment در حضور checkpoint نهایی، بسته می‌ماند. lock فایل انحصاری است؛ حذف خودکار stale lock یا checkpoint مجاز نیست. رد قطعیِ احراز هویتِ درخواست تازه اثر DB ندارد و pending تازهٔ آن پاک می‌شود تا typo ابزار را قفل نکند.
6. Recovery همین Staging به **root/SSH/TTY و Password فعلی همان OWNER** نیاز دارد؛ PIN قبلی لازم نیست. نبود/خطای Password هیچ PIN failure جدیدی نمی‌سازد. بررسی Password خارج transaction و recheck credentialVersion زیر lock انجام می‌شود؛ همزمانی تغییر Password اجازهٔ بازیابی با مدرک قدیمی نمی‌دهد. Recovery فقط PIN/lock و epochها را تغییر می‌دهد، identity یا Password را جایگزین نمی‌کند و تمام FULL/PENDINGهای قبلی را باطل می‌کند. فراموشی Password از این مسیر حل نمی‌شود؛ نگه‌داری آن در vault شخصی پیش‌نیاز است، نه دلیلی برای SQL reset.
7. STARTED/DENIED/SUCCEEDED با فیلدهای allowlist و commandId در Audit خصوصیِ durable ابزار ثبت می‌شوند؛ موفقیت DB/receipt/Audit همچنان تراکنش واحد است. credential/username در این رویدادها نیست. شکست Audit پیش از effect مانع اثر است؛ شکست بعد از commit با pending/receipt یا checkpoint قابل reconcile است و موفقیت کاذب چاپ نمی‌شود. فایل OS در برابر root، WORM نیست. archive رمزگذاری‌شده و رسید بیرون سرور کنترل جبرانی Staging‌اند؛ سرویس لاگ جدید یا تغییر retention کلی پروژه ساخته نمی‌شود. سقف فایل باعث توقف است، نه حذف خودکار تاریخچه.
8. پیش از ایجاد/بازیابی، شواهد امنیت Core/Admin با حداقل پنج دقیقه مهلت و نبود marker توقف لازم‌اند. receipt بازبینی‌شدهٔ restore و کپی خارج سرور حداکثر ۲۴ ساعت عمر دارد و به SHA-256 بستهٔ مورد تأیید متصل است. این profile مخصوص ceremony است؛ SLO/RPO/retention عمومی پروژه را تعیین نمی‌کند. receipt در این نوبت برای سرور جعل یا نصب نمی‌شود.
9. بکاپ هویت فقط شش جدول Admin را با pg_dump snapshot سازگار و role خصوصی recovery می‌گیرد؛ SELECT دو جدول session/grant فقط با فایل جدا `admin-staging-owner-permissions.sql` به خواندنی‌های موجود همان role در Staging افزوده می‌شود و HBA موجودِ gateway میزبان حفظ می‌شود؛ game/chat/hidden state در دامنهٔ آن نیست. dump، checkpoint و capsule کلیدهای موردنیاز هویت، پیش از نوشتن فایل با AES-256-GCM و scrypt و salt/nonce تصادفی رمزگذاری می‌شوند. عبارت decrypt مستقل، حداقل ۲۰ نویسه و فقط تعاملی است؛ بیرون سرور نگه‌داری می‌شود. سقف اندازه محدود است. این archive حاوی credentialهای زیرساخت به‌شکل رمزگذاری‌شده است، نه Password/PIN خام OWNER؛ decrypt key و archive نباید تنها روی همان VPS بمانند.
10. ابزار restore-test فقط کپی اپراتور، خارج نشست SSH، و container جدیدِ اختصاصی Docker محلی با network=none، بدون port/host volume و دادهٔ tmpfs را می‌پذیرد؛ هیچ target URL نمی‌گیرد. AEAD پیش از تحویل داده به PostgreSQL بررسی می‌شود. schema و grants از فایل‌های بازبینی‌شده ساخته، داده در transaction واحد restore و owner binding/FK/trigger/privilege بررسی می‌شود؛ container خودش حذف می‌شود. سپس receipt متصل به hash archive صادر می‌شود. `--disable-triggers` فقط در این target یک‌بارمصرف و با privilege اپراتور است؛ runtime امتیاز تازه‌ای نمی‌گیرد. این روش مبتنی بر رفتار مستند [pg_dump](https://www.postgresql.org/docs/18/app-pgdump.html) و [pg_restore](https://www.postgresql.org/docs/18/app-pgrestore.html) است.
11. restore روی محیط سرویس‌دهنده عمل جداست و این ابزار انجامش نمی‌دهد. پیش از بازگشایی پس از disaster restore، checkpoint مستقل باید reconcile و signing key نشست عوض شود تا snapshot قدیمی نشست معتبر زنده نکند؛ PIN pepper/command key بی‌برنامه عوض نمی‌شوند. قفل عادی با Recovery خصوصی باز می‌شود، نه restore کل دیتابیس مشترک.
12. تغییر Password/PIN خود OWNER در داشبورد با Password/PIN فعلی، CSRF، Audit و ابطال همهٔ نشست‌ها حفظ می‌شود. احراز هویت مجدد برای تغییرات حساس و ابطال نشست با [راهنمای OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) همسو است. Password + PIN ثابت همچنان MFA مستقل یا مقاوم به فیشینگ نیست.

## Alternatives

- ادامهٔ دو کلید برای Staging: تضمین جدایی proof بیشتر دارد، ولی مطابق درخواست جدید مالک نیست؛ برای محیط‌های دیگر حفظ می‌شود.
- SSH root بدون policy، تأیید عمل، checkpoint، Password در Recovery و backup rehearsal: اختیار بیش‌ازحد ضمنی و ریسک restore/replay دارد؛ رد.
- Forgot Password عمومی، فایل credential موقت، username پیش‌فرض یا SQL مستقیم: مرزهای هویت و Audit را می‌شکند؛ رد.
- افزودن vault/IdP/service خارجی: برای این scope لازم نیست؛ custody شخصی و ابزار خصوصی کافی‌اند.

## Consequences و بررسی امنیت

اعتماد Staging به root/کلید SSH متمرکزتر و جدایی سازمانیِ دو امضا حذف می‌شود؛ سرقت root یا دست‌کاری release/policy توسط root خارج توان این کنترل‌هاست. Password لازم برای Recovery جلوی استفادهٔ صرف از credential DB یا اشتباه اپراتوری را می‌گیرد، اما root مخرب را مهار نمی‌کند. ریسک گم‌شدن همزمان SSH/vault/backup، memory/swap/ضبط ترمینال و فراموشی Password باقی است. capsule رمزگذاری‌شده محرمانه است و receipt به‌تنهایی secret نیست، ولی فقط نسخهٔ root-owned بازبینی‌شدهٔ آن به ceremony اعتماد می‌دهد.

کنترل SSH/TTY و Password در composer اجرا می‌شود، نه داخل PostgreSQL. credential خصوصی recovery خودش مجوز تغییر ستون‌های PIN/lock دارد؛ نباید به runtime یا شخص فاقد اختیار اپراتوری داده شود. HBA خصوصی و custody بیرون کانتینر runtime مرز این اختیارند؛ این طرح مدعی مهار DBA، superuser یا root مخرب نیست. استفاده از role نوشتنیِ recovery برای dump خواندنی، tradeoff صریح Staging است؛ اضافه‌کردن role/daemon جدید برای اپراتور root همان میزبان در این scope لازم نیست.

برای Production این کاهش کنترل قابل تعمیم نیست. هیچ فاز دو، عملیات مالی/مدیریت مدیران، deployment، public ingress یا ساخت OWNER واقعی با تحویل کد مجاز نشده است.

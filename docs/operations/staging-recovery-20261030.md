## علت و اصلاح

Nginx و nginx-common در ۲۸ اکتبر ساعت ۰۶:۲۳ UTC از `1.24.0-2ubuntu7.18` به `…7.19` ارتقا یافته بودند؛ کنترلر همچنان نسخهٔ قبلی را می‌خواست. اولین شکست core renewal در ۰۷:۰۲ UTC ثبت شد. guard پیش از دانلود/scan رد می‌کرد، deadline جلو نرفت و هر دو expiry در ۲۹ اکتبر ۰۱:۲۱ UTC سرویس‌ها را بستند. Admin نیز طبق policy از deadline Core عبور نمی‌کند. عامل خودِ ارتقای OS از شواهد این بازیابی تعیین نشده است.

فایل‌های بستهٔ نصب‌شده با `dpkg --verify` بدون اختلاف بودند؛ metadata مخزن noble-security مشاهده و سازگاری با `nginx -t`، TLS و مسیرهای فعلی بررسی شد. hash باینری master واقعی Nginx با باینری نصب‌شده برابر است. فقط `hostPackages` در کنترل Core به نسخهٔ **دقیق بررسی‌شده** بازبسته شد؛ تمام pins/files/identities دیگر، کنترل Admin و کد هر دو کنترلر بدون تغییر ماندند. پذیرش خودکار نسخهٔ دلخواه، downgrade، خاموش‌کردن unattended update یا تغییر severity/freshness اضافه نشد.

## Qualification و بازپذیری

- دانلود واقعی و تازهٔ دیتابیس [رسمی Trivy](https://trivy.dev/docs/dev/configuration/db/) روی خود سرور؛ اسکن همان هفت ایمیج، **صفر HIGH/CRITICAL/UNKNOWN**. PostgreSQL و Redis هرکدام یک MEDIUM مجاز دارند؛ سایر ایمیج‌ها صفر finding داشتند.
- ۱۸ تست کنترلرهای موجود و پنج تست guard بازیابی موفق‌اند: نسخه/دامنهٔ بررسی‌نشده رد می‌شود، verifier اصلی با pin قدیمی رد و با pin بازبسته می‌پذیرد، guard پراکسی/TLS حفظ و پاسخ نامطلوب به موفقیت تبدیل نمی‌شود.
- وضعیت و timerهای جدید از همان `normal_expiry` و `scan_deadline` و metadata واقعی مشتق شدند: **۳۰ اکتبر ساعت ۲۲:۴۸:۵۰ تهران**. پنجره ۲۴ساعته، مستقل و محدود باقی است؛ تاریخ دلخواه یا استثنا ثبت نشد.
- ورودی عمومی زیر maintenance ماند؛ API، Worker، Web و سپس Bot با همان کانتینرها راه افتادند. Admin از مسیر عادی systemd و `--admit` شروع شد؛ guard آن اجرا شد. هر دو verifier و native healthها پیش از بازگشایی موفق شدند. پیش از هر reload، `nginx -t` اجرا شد.
- اجرای واقعی renewal serviceهای Core و Admin موفق شد؛ بعداً اجرای ساعت بعد Core در `23:01:35 UTC` نیز موفق ثبت شد. هر چهار timer فعال و هر دو expiry واقعاً به همان مهلت بالا اشاره می‌کنند. دانلود/تمدید روی سرور انجام می‌شود و به رایانهٔ مالک وابسته نیست. ثابت‌ماندن deadline در اجرای دارای همان UpdatedAt، نتیجهٔ صحیح `unchanged` است.

## HTTPS و حفاظت اطلاعات

از بیرون سرور و با TLS معتبر، Web و Login Admin پاسخ ۲۰۰ و مسیرهای محافظت‌شدهٔ `/v1/me` و `/v1/admin/me/access` پاسخ ۴۰۱ دارند. هر ۱۹ کنترل HTTPS/CSRF/default-deny مصوب فاز دوم موفق‌اند؛ مسیرهای عمومی Bootstrap/Recovery/Forgot/Reset همچنان ۴۰۴ و Admin روی API بازیکنان ۴۰۴ است. مرورگر ناشناس Login فارسی/RTL، Password-only پیش از مرحله PIN و نمایش موبایل/دسکتاپ را تأیید کرد؛ credential وارد نشد. Backend، PostgreSQL و Redis پورت عمومی ندارند.

مالک قبل و بعد یک OWNER فعال با credentialVersion=2، sessionEpoch=2، authorizationVersion=1، PIN failures=0 و بدون lock داشت؛ PASSWORD_CHANGED همان یک رویداد قبلی و PIN_CHANGED صفر ماند. username، verifier، Password، PIN، cookie یا token واقعی خوانده نشد. هیچ تغییر مستقیم دادهٔ کسب‌وکار، Migration، restore دیتابیس، تغییر grant/نقش یا نصب فاز سوم انجام نشد؛ ۱۹ Migration و نبود جدول فاز سوم حفظ‌اند. پردازش عادی برنامه‌ها پس از راه‌اندازی از سر گرفته شد. Production و فاز چهارم تغییر نکردند.

## تلاش‌های ناموفق و حدود نتیجه

نخستین Qualification با تلاش برای نگهداری دو کپی دیتابیس اسکن، به کمبود فضای موقت رسید؛ فایل ناقص همان تلاش پاک و دانلود در یک کش خالی مستقل انجام شد. منبع رسمی، timestampها و تمام scanها حفظ شدند؛ PostgreSQL، بکاپ‌ها یا ایمیج‌ها پاک نشدند. پس از انتقال کنترل‌شدهٔ کش معتبر، فایل موقت حذف شد و حدود ۲٫۸۵ GiB آزاد باقی ماند.

اولین بازگشایی با مشاهدهٔ 503 فوراً به containment ایمن برگشت. در تکرارِ دارای ثبت پاسخ، انتظار محدود reload نشان داد پاسخ قدیمی 503 در کمتر از یک ثانیه به 200/401 صحیح تبدیل می‌شود. پاسخ 500، 403 نامنتظره یا TLS نامعتبر پذیرفته نمی‌شود؛ timeout محصول/حد امنیتی تغییر نکرد. ابزار کمکی گردآوری گزارش ابتدا به‌علت خطای نحوی اجرا نشد و آن تلاش به PASS تبدیل نشد؛ verifierها، سرویس‌ها، timerها و renewal در گردآوری مستقل بعدی موفق‌اند. رویدادهای هر تلاش در شواهد حفظ‌اند.

ورود واقعی OWNER، بازی انسانی Telegram و آزمون ظرفیت/Load/Stress/Soak اجرا نشدند. تغییر بعدی بسته‌های pinشدهٔ میزبان همچنان بازبینی و Qualification می‌خواهد؛ کنترل تطبیق نسخه حفظ شده است. قطع feed یا یافتهٔ مسدودکننده می‌تواند طبق همان policy محدود دوباره containment ایجاد کند. این نتیجه، مجوز نصب فاز سوم یا تأیید ظرفیت نیست.

کدهای عملیاتی، snapshot کنترل‌ها، گزارش scan و رویدادها فقط در پوشهٔ خصوصیِ درج‌شده در JSON روی سرور/رایانه نگه‌داری شده‌اند؛ هیچ secret در Git یا این سند قرار ندارد.
